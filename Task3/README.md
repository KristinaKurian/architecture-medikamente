# Задание 3. Стратегия защиты данных

## 1. Какие данные нужно защищать

В «Медикаменте» персональные и медицинские данные хранятся в Excel, PDF/JPG и 1С. При переходе на новую платформу необходимо защитить их как при хранении, так и при передаче между системами.

Разделим данные по уровню риска:

| Данные | Класс | Почему нужна защита | Риск |
|---|---|---|---|
| Медкарты, диагнозы, анализы | `RESTRICTED_MEDICAL` | Содержат врачебную тайну | Критический |
| Записи к врачу, история посещений | `CONFIDENTIAL_PII`, `RESTRICTED_MEDICAL` | Раскрывают информацию об обращении пациента | Критический |
| ФИО, телефоны, адреса, договоры | `CONFIDENTIAL_PII` | Позволяют установить личность пациента | Высокий |
| Платежи, суммы, чеки | `CONFIDENTIAL_FINANCE` | Возможны утечка финансовых данных и мошенничество | Высокий |
| Кадровые документы, зарплаты | `RESTRICTED_HR` | Содержат персональные данные сотрудников | Высокий |
| Закупки, остатки ТМЦ | `INTERNAL`, `CONFIDENTIAL_FINANCE` | Содержат внутреннюю и коммерческую информацию | Средний |
| Резервные копии и выгрузки | Класс исходных данных | Могут содержать копии медицинских и персональных данных | Зависит от содержимого |

Уровни риска используются для определения приоритетов внедрения защиты, а не как официальные уровни защищённости ИСПДн.

## 2. Как будем защищать данные

### Защита при хранении (at rest)

- **Сервер и файловая 1С:** проверить права доступа, включить шифрование дисков с помощью BitLocker.
- **Медицинская платформа:** шифровать базу данных, документы и резервные копии. Для особо чувствительных полей при необходимости использовать дополнительное шифрование.
- **Ключи шифрования:** хранить отдельно от данных, например в Vault/KMS.
- **Резервные копии:** хранить отдельно от основного сервера, шифровать и регулярно проверять восстановление.

### Защита при передаче (in transit)

- **Портал, мобильное приложение и API:** использовать HTTPS/TLS.
- **Внутренние сервисы и лаборатория:** передавать данные по защищённым каналам, при необходимости использовать mTLS.
- **1С и файловый сервер:** ограничить сетевой доступ, использовать шифрование соединений там, где оно поддерживается.
- **ККМ:** проверить используемый протокол и разрешить подключения только с необходимых устройств.

Шифрование не заменяет проверку прав. Даже после входа в систему сотрудник должен получать доступ только к данным, которые нужны ему для работы.

## 3. Автоматический контроль

Для поиска проблем и отслеживания подозрительных действий предлагаем следующие проверки.

| Что проверяем | Инструмент | Результат |
|---|---|---|
| Доступ к медицинским документам | Windows Audit, Wazuh | Уведомления о массовом просмотре и выгрузках |
| Лишние копии персональных данных | Presidio | Поиск файлов с конфиденциальной информацией |
| Защиту соединений | Проверки TLS и сертификатов | Обнаружение небезопасных подключений |
| Права доступа через API | Автотесты в CI/CD | Проверка, что пациент не может открыть чужие данные |
| Секреты и ошибки в коде | Gitleaks, Semgrep | Обнаружение проблем до выпуска новой версии |
| Резервные копии | Мониторинг заданий и тест восстановления | Проверка, что данные можно восстановить |

В журналы аудита нельзя записывать пароли, ключи, диагнозы и содержимое медицинских документов.

## 4. Программные и аппаратные средства

Полный перечень инструментов, их назначение и приоритет внедрения приведены в [реестре средств защиты](protection-tools-register.md).

На первом этапе достаточно проверить и настроить существующие Windows Server, Active Directory и 1С, а также защитить резервные копии.

При разработке новых сервисов добавляются TLS, управление ключами, мониторинг и автоматические проверки.

## 5. Как проверить результат

После внедрения необходимо убедиться, что:

1. Медицинские данные и резервные копии зашифрованы.
2. Передача конфиденциальной информации выполняется по защищённым каналам.
3. Пользователи не могут получить доступ к чужим медицинским документам.
4. Подозрительные действия фиксируются и вызывают уведомления.
5. Данные успешно восстанавливаются из резервной копии.
