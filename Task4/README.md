# Задание 4. Узкие места при миграции «Медикаменте»

## 1. Текущая ситуация

Сейчас компания использует Excel, файловую 1С и общий диск для хранения документов. Все основные системы работают на одном сервере Windows Server 2022.

Компания планирует открыть новые филиалы, внедрить личный кабинет пациента и увеличить объём данных в пять раз.

Основные сложности при переходе на новую систему — перенос данных, производительность, интеграции с 1С и обеспечение бесперебойной работы.

Поскольку замеров производительности нет, рассматриваем возможные проблемы, которые необходимо проверить до миграции.

## 3. Основные проблемы и решения

| Категория | Возможные проблемы | Решение | Приоритет |
|---|---|---|---|
| Инфраструктура | Один сервер, недостаточно ресурсов при росте нагрузки | Проверить CPU, RAM, диски и сеть. Провести нагрузочные тесты | P0 |
| Данные | Дубли в Excel, ошибки переноса документов и пациентов | Очистить данные, переносить частями и проверять результат | P0 |
| Интеграции | Медленная работа 1С, ККМ и будущего API лаборатории | Использовать адаптеры, тайм-ауты и повторные запросы с защитой от дублей | P0 |
| Приложение | Двойная запись к врачу, медленные запросы к базе | Обеспечить атомарное бронирование, настроить индексы и оптимизировать запросы | P0 |
| Миграция | Простои и потеря данных при переходе | Переходить поэтапно, предусмотреть резервные копии и откат | P1 |
| Команда | Три IT-специалиста не смогут одновременно поддерживать много новых сервисов | Упростить архитектуру, распределить ответственность и настроить мониторинг | P1 |

**P0** — решить до переноса основных данных.  
**P1** — подготовить до полноценного запуска.

## 4. Предлагаемая архитектура

На первом этапе не стоит сразу переходить на микросервисы. Предлагаю использовать модульный монолит с отдельными бизнес-модулями:

- Пациенты и запись на приём.
- Медицинские карты и документы.
- Оплата и интеграция с 1С.
- Интеграция с лабораторией.

Для новой платформы используем PostgreSQL и отдельное файловое хранилище для документов. Обмен с внешними системами выполняем через адаптеры.

Это позволит развивать систему постепенно. Если отдельный модуль начнёт создавать высокую нагрузку, его можно будет вынести в самостоятельный сервис.

## 5. Как проводить миграцию

1. **Подготовка.** Проверить текущее оборудование, объём данных и зависимости между системами.
2. **Перенос данных.** Очистить Excel-файлы от дублей, перенести пациентов и медицинские документы с проверкой связей.
3. **Запуск записи на приём.** Перевести один процесс на новую платформу, оставив остальные в существующих системах.
4. **Подключение интеграций.** Постепенно подключить 1С, ККМ и лабораторию.
5. **Проверка нагрузки.** Протестировать систему перед подключением новых филиалов.

Во время перехода для каждого вида данных должен быть определён основной источник, чтобы изменения не терялись между старой и новой системами.

## 6. Что проверить перед запуском

| Проверка | Ожидаемый результат |
|---|---|
| Нагрузка ×5 | Система выдерживает согласованную нагрузку без недопустимого роста задержек и ошибок |
| Одновременная запись | Один слот нельзя забронировать дважды |
| Миграция данных | Пациенты, записи и документы перенесены без потерь |
| Недоступность 1С или лаборатории | Основные функции продолжают работать, операции не дублируются |
| Восстановление | Данные можно восстановить из резервной копии |
| Мониторинг | Ошибки и задержки отображаются в системе мониторинга |

Допустимое время ответа и другие показатели производительности нужно определить после первых замеров.

## Вывод

Главные риски миграции связаны с качеством исходных данных, производительностью сервера и интеграциями.

Для «Медикаменте» оптимально начать с модульной архитектуры, переносить процессы постепенно и проверять работу системы под нагрузкой.

Это позволит снизить сложность миграции и сохранить возможность дальнейшего перехода к микросервисам, если в них появится необходимость.
